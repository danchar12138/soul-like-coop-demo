## TD-001：首个 Demo 的标志性武器选「太刀」

**背景**
任务要求在三种候选武器原型中比较制作成本、动作表现和战斗辨识度，
然后自动选定一种作为标志武器并记录理由。

**三个候选原型**

| 原型 | 动作设计要点 | Blender 制作成本 | 战斗辨识度 | 战斗深度 |
|------|--------------|------------------|------------|----------|
| A 单手直剑 | 砍、刺、盾击；动作简单 | 低（1 个网格 + 少量骨骼） | 中（最"标准"，玩家一眼看懂，但记不住） | 中 |
| B 双手巨剑 | 慢、重、大范围横扫；蓄力明显 | 中（网格大但结构简单，不需要精细握持） | **高**（挥砍弧线大、轮廓醒目） | 中高（惩罚窗口大、风险回报清晰） |
| C 太刀 | 中距离横斩、居合突进、拔刀收刀 | 低（细长网格，比巨剑更省面数） | **高**（刀身细长 + 居合蓄力的姿态辨识度极强） | **高**（进退拉锯、连招节奏、位移斩） |

**决定：选 C 太刀。**

**理由**
1. **制作成本最低的一项**。刀身是一条细长盒子 + 一个护手 + 一个刀柄，
   总共 3 个盒子就能做出可辨认的轮廓，比巨剑少一半体积，也比直剑
   少了盾牌组件。
2. **战斗辨识度最高。** 细长刀身 + 每次收招回到"残心"姿态，
   即使只用几何体占位，从远处也能一眼分辨是在挥刀还是在跑动。
3. **对验证战斗系统最有价值。** 太刀的"居合"天然是一段
   **蓄力 → 爆发 → 长收招** 的完整曲线，正好用来验证
   `AttackData` 里 `chargeable / lunge_speed / recovery` 三组参数
   是否真的能做出"高风险高回报"。巨剑的蓄力更接近单纯的"更慢更疼"，
   测不出位移与判定的配合。
4. **三段连招的节奏差异最容易做出来。** 见 `tools/generate_weapons.gd`
   里的参数：三段轻攻击的起手时间是 0.30 / 0.26 / 0.42 秒，
   总时长 0.74 / 0.72 / 1.08 秒，伤害 18 / 21 / 30。
   第三段明显更慢更重，收招也更长。这种"由快转重"的节奏是太刀的
   标准表现手法，而且它天然制造了"要不要打第三段"的决策点。

**代价**
- 没有盾牌，后续要加格挡体系时需要重新设计姿势。
  → 已在 `战斗设计.md` 的"后续扩展"里记录。
- 居合的突进距离（9 m/s 位移）需要额外的碰撞把关，
  否则会冲进墙体。已在 `AttackData.lunge_speed` 的注释里标注。

**后续**：三种武器的 `WeaponData` 结构已经完全数据驱动，
追加巨剑/直剑只需新增 `.tres`，不必改任何代码。

## TD-002：用生成脚本产出 `.tscn` 和 `.tres`，不手写

**背景**
需要创建 7 个场景和 8 个武器资源。`.tscn` / `.tres` 是文本格式，
看起来可以手写。

**决定**
写 `tools/build_scenes.gd` 和 `tools/generate_weapons.gd`，
用 Godot 自己的 `PackedScene.pack()` / `ResourceSaver.save()` 产出。

**理由**
1. `AttackData` 有 40 多个字段。手写 `.tres` 时漏掉一个字段**不会报错**，
   会静默使用默认值。调参时改了 `windup` 却发现没生效，会浪费大量时间。
2. `.tscn` 里的 `[node parent="..."]` 路径、`ExtResource` ID、
   `Transform3D` 的 12 个浮点数都极易写错，且报错信息指向不明。
3. 用代码生成时，参数以命名参数形式集中在一处，改一个数值能立刻
   看出它属于哪条攻击，可读性反而比 `.tres` 更好。
4. **节点路径与脚本里的 `NodePath` 天然一致**，因为两边都是我自己写的。

**代价**
- 生成脚本会**覆盖**目标文件。手改 `.tres` 后重跑生成会丢失修改。
  → 已在两个脚本顶部和 `AGENTS.md` 里明确写出这条。
- 生成脚本必须以**场景**方式运行（`godot --headless res://tools/builder.tscn`），
  不能用 `--script`。因为被加载的脚本引用了 `GameConfig` / `EventBus`
  等 Autoload，而 `--script` 模式下引擎不初始化 Autoload，
  编译器会报 `Identifier not found: GameConfig`。

## TD-003：输入映射在运行时用代码注册

**背景**
Godot 的输入映射通常写在 `project.godot` 的 `[input]` 段。

**决定**
写在 `scripts/core/input_setup.gd`，在 `_enter_tree()` 里注册。

**理由**
1. `project.godot` 里的 `Object(InputEventKey,...)` 是引擎内部的
   序列化格式，手写极易出错且完全不可读。
2. 集中在一处便于后续做按键重绑定界面 —— 那是本项目的既定扩展方向。
3. 用 `physical_keycode` 而非 `keycode`，支持非 QWERTY 布局。

**代价**：无法在 Godot 编辑器的"项目设置 → 输入映射"里直观看到。
→ 在 `input_setup.gd` 顶部的注释里放了完整的按键表。

## TD-004：状态机用「单枚举 + 优先级表」，不用节点式 State 模式

**背景**
角色有 12 种动作状态（待机/冲刺/闪避/攻击/蓄力/受击硬直/破防/被处决/
死亡/倒地/复活中/胜利）。常见做法是每个状态一个 Node。

**决定**
用 `CombatState.State` 枚举 + `CombatState.PRIORITY` 优先级表。
所有状态迁移走 `CharacterStateMachine.request_state()`。

**理由**
1. **"谁能打断谁"是战斗手感的核心规则**，必须一眼可见。
   优先级表把这条规则变成一个可以直接读、直接调的数值表。
   节点式状态机里这条规则会散落在各状态的 `can_transition_to()` 中。
2. 本项目只有 3 种角色（主角/木桩/Boss），状态逻辑都很短，
   节点式会带来 12 个文件 × 3 份的样板。
3. **联机同步只需要传一个 int**，而不是一堆布尔标志。
   `PlayerSync` 直接把 `get_state()` 的整数发给其他玩家。
4. 天然解决"动作卡死"：`request_state` 里有超时兜底
   （`CharacterStateMachine._process` 的 `_timeout`），
   任何状态忘记退出都会被强制拉回待机。

**代价**：状态逻辑集中在一个大 `match` 里。若将来状态数超过 30 个，
应重构。已在代码注释里标注这个阈值。

## TD-005：受击盒按阵营分层，不共用碰撞层

**背景（这是一个真实踩过的坑）**
最初为了让攻击判定"用同一套 mask 就能打到玩家和敌人"，
把**所有**受击盒同时挂在 `player_body(2)` 和 `enemy_body(3)` 上。

**后果**
敌人的攻击 mask 含有 layer 2，于是**命中了另一个敌人的受击盒**。
表现：两个训练木桩互相砍。在自动化测试里暴露为
"玩家一次挥击扣了 30 血"（自己的 18 + 隔壁木桩打的 12），
排查了相当一段时间才定位到碰撞层。

**决定**
按阵营分层，掩码在 `Hitbox` 里定义为常量：

| 阵营 | 受击盒层 | 攻击 mask |
|------|----------|-----------|
| 玩家 | `player_body(2)` | `enemy_body(3) \| destructible(6)` = 36 |
| 敌人 | `enemy_body(3)` | `player_body(2) \| destructible(6)` = 34 |

**理由**
1. "谁能打谁"由碰撞层**一地定义**，代码里不需要写任何 `if` 判断。
   物理引擎负责过滤，比在 `_check_overlaps()` 里判断更不容易出错，
   也更快。
2. 这样天然支持"玩家攻击不误伤队友"，未来加友军伤害只需改掩码。

**代价**：`Hitbox` 需要在场景里正确设置 `attack_layer` 与
`target_layers` 两个导出值。已在 `build_scenes.gd` 里定义
`L_PLAYER_BODY` 等常量集中管理。

## TD-006：命中停顿只减速本地动画，绝不用 `Engine.time_scale`

**背景**
任务书第 4.4 条明确要求："命中停顿不能直接冻结整个联机世界。
应区分本地表现效果与实际战斗状态。"

**决定**
`HitstopManager` 只把**攻击者自己的** `AnimationTree` / `AnimationPlayer`
的 `speed_scale` 压到 0.04。物理、网络、其他玩家、Boss 的攻击计时
全部照常推进。

**理由**
1. `Engine.time_scale` 会影响所有玩家和所有物理。A 玩家打出重击的
   顿帧会让 B 玩家卡顿，属于把本地表现泄漏成了全局状态。
2. 更严重的是：如果顿帧把 Boss 的攻击计时也暂停了，玩家就能用
   **顿帧逃避伤害** —— Boss 的起手在顿帧期间不走，玩家的闪避窗口
   被动延长。这会破坏类魂战斗的公平性。
3. 只改动画速度的副作用是"动画卡住了但攻击时序还在推进"。
   本项目里 `AttackController` 的时间推进用 `_process(delta)`，
   而 `_process` 的 delta 不受 `speed_scale` 影响，两者天然保持一致。

**代价**：顿帧期间角色的位移（`lunge_speed` 产生的前冲）不会减速，
视觉上有一点不协调。当前数值（0.045~0.13 秒）下几乎不可察觉，
若将来把顿帧拉长需要一并处理。

## TD-007：地形破坏由权威端结算，客户端只播表现

**背景**
任务书第 6 条要求："联机环境下，由权威端确认破坏结果并向其他玩家
同步，不能让每个客户端独立决定某个地形是否已经被摧毁。"

**决定**
- 权威端：`TerrainManager.apply_damage_authoritative()` 直接结算。
- 客户端：`TerrainManager.request_damage()` → `_rpc_request_damage`
  → 主机校验后结算 → `_rpc_piece_destroyed` 广播 → 客户端
  `force_destroy_from_network()` **直接销毁，不重算**。

**理由**
1. 如果各端各自扣耐久，网络延迟会让结果分叉（A 端显示已碎、
   B 端显示还有一块），玩家会撞上看不见的墙。
2. 客户端**本地先播一点反馈**（`piece._flash()` 闪白），
   这样操作的即时感不会因为等主机回包而变差。
   这是"本地表现"与"权威状态"分离的标准做法。
3. 主机做了基本的合理性校验：伤害 > 500 的请求直接拒绝并告警，
   防止作弊客户端秒拆地形。

**代价**：客户端看到的碎裂比主机晚一个 RTT（局域网内 <5 ms，
可接受）。若要更跟手可以做乐观预测 + 回滚，但当前规模不值得。

## TD-008：玩家位置由客户端权威、主机校验

**背景**
四人合作里，玩家位置有两种主流方案：
(a) 服务器权威 —— 服务器算位置，客户端发输入。
(b) 客户端权威 —— 客户端算位置，上报给服务器校验。

**决定：(b)，并加上主机侧的速度校验。**

**理由**
1. 方案 (a) 的输入延迟直接体现在操作手感上。本项目的**第一优先级
   是战斗手感**，让玩家的移动等一个 RTT 回包是不可接受的。
2. 局域网环境下作弊风险低（本项目不做公网匹配，
   任务书也明确排除账号系统和商业服务器）。
3. 主机侧的校验很轻量但有效：单次上报位移超过
   `MAX_SPEED_TOLERANCE` 对应的距离就丢弃该帧并告警。

**代价**：作弊客户端理论上可以"卡着上限速度瞬移"。
公网版本必须换成方案 (a) 或加入服务端重放。已在
`架构说明.md` 的"已知限制"里记录。

**注意区分**：位置是客户端权威，**战斗结果不是**。
伤害、Boss 血量、地形破坏全部仍然是主机权威（TD-007）。

## TD-009：手写 RPC 同步，不用 `MultiplayerSynchronizer`

**背景**
Godot 4 提供了 `MultiplayerSpawner` + `MultiplayerSynchronizer`
这套高层多人 API。

**决定**
玩家位置同步用手写的 `scripts/net/player_sync.gd`（约 130 行）。

**理由**
1. `MultiplayerSynchronizer` 需要一份 `SceneReplicationConfig` 资源，
   在代码里构造它很别扭，而且要额外维护一个和场景绑定的配置文件。
2. 它的插值策略是固定的，不适合"每个客户端权威自己的角色"这种模式
   （它更倾向服务器权威 + 客户端插值）。
3. 手写 RPC 的行为**完全可预期、可打日志、可单步调试**。
   同步逻辑一旦出问题，排查成本远高于这 130 行代码本身。
4. 场景本身仍然用 `MultiplayerSpawner` 的等价做法
   （`LevelManager` 在主机侧统一生成玩家，通过 `set_multiplayer_authority`
   分配权限），不引入额外依赖。

**代价**：位置更新率、插值参数需要自己调。
已放进 `GameConfig`（`CLIENT_INTERP_BUFFER`）。

## TD-010：音效先用程序合成占位，并明确标注

**背景**
项目当前**没有**任何正式音效资源。

**决定**
`scripts/core/audio_manager.gd` 用 `AudioStreamWAV` 在运行时合成
8 种占位音（挥空、轻/中/重命中、砍石头、闪避、死亡）。

**理由**
1. 任务书 4.4 第 3 条要求"命中不同类型的目标时有相应的音效或
   占位声音" —— 明确允许占位音。
2. **打击感的验证需要听觉差异**。如果轻击和重击听起来一样，
   就没法判断"重击是否真的更重"。这比"有没有好听的音效"重要得多。
3. 合成音可以先用，同时把接口留好：`AudioManager._resolve_stream()`
   会**优先加载** `res://assets/audio/<key>.wav`。以后放进正式音效
   文件即可自动生效，不需要改任何调用点。

**如实说明**：这些不是正式音效，音色粗糙。
不能因为"有声音了"就认为音频部分已完成。

## TD-010 补记（2026-10-12）：占位音降级为回退路径

`assets/audio/` 现已放入 14 个离线合成的 WAV（`tools/generate_audio.py`），
`_resolve_stream()` 会优先加载它们，**上面描述的运行时合成只在文件缺失时触发**。

**但 TD-010 的结论没有被推翻**：新文件同样是**程序合成**的产物，
只是从"运行时合成"变成"离线合成 + 更多 DSP 手法"（ADSR、失谐叠加、
粉噪声、逐样本扫频滤波、软削波、无缝循环）。
它们仍然不是专业录音，仍然不能当作"音频部分已完成"。
详见 `assets/audio/README.md` 的"已知不足"。

**为什么保留运行时合成这条路径**：它是资源缺失时的降级保障 ——
任何时刻删掉 `assets/audio/*.wav` 游戏都不会静音。删掉会让系统变脆。

## TD-011：朝向计算统一走 `MathUtil`，并写测试锁死

**背景（真实踩过的第二个坑）**
Godot 的 `Node3D` 约定**前方 = -Z**。从方向 `d` 求绕 Y 的朝向角，
正确公式是 `atan2(-d.x, -d.z)`。

网上大量教程写的是 `atan2(d.x, d.z)`，那是给"前方 = +Z"的模型
（不少 glTF 导出就是这样）用的。

**后果**
写成 `atan2(d.x, d.z)` 时，角色会**转 180 度**：
看起来"朝某个方向走"，但攻击判定盒（挂在局部 `-Z` 方向的
`hit_offset`）悬在**背后**，永远打不中人。
更麻烦的是这个错误不会报任何错，只会表现为"攻击打不到"，
很容易误判成判定盒尺寸或位置配错了。

**决定**
1. 所有朝向计算集中到 `scripts/core/math_util.gd` 的
   `yaw_from_direction()` / `yaw_towards()`。
2. 在自动化测试里加了 `T13` 专门锁死这个约定：
   断言 `+Z → -PI`、`-Z → 0`、`+X → -PI/2`，
   并实测"角色 forward 与目标方向的点积 = 1.0"。

**理由**
这个 bug 的症状（打不中）和它的原因（朝向）相距很远，
一旦复发就要重新排查一遍。用测试锁死成本极低。

**代价**：无。`MathUtil` 是纯静态函数，没有运行时开销。
