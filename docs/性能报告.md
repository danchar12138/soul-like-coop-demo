# 性能报告

本报告对应已知问题 **K-09「未做性能测试，不知道碎片满屏时的帧率」**。

所有数据由自动化测试生成，原始读数见：

- `tests/性能结果.txt` —— 主测试的 8 个场景（脚本自动生成，不允许手改）
- `tests/性能上限探针.txt` —— 碎片数量 → 物理耗时 的拐点
- `tests/性能最坏情况探针.txt` —— 60 个碎片全程飞行（限内理论最坏）

一键复现：

```bash
cd <项目根目录>
bash tests/run_perf_test.sh              # 全部（约 75 秒）
bash tests/run_perf_test.sh --main-only  # 只跑主测试（约 35 秒）
```

## 一、测试方法

### 1.1 为什么是在无头（headless）下测，以及它测不到什么

测试全部跑在 `godot --headless` 下。无头模式使用 **dummy 渲染器**，
它**不渲染任何画面**。因此：

| 指标 | 无头下是否可信 | 说明 |
|------|----------------|------|
| 物理帧间隔（墙钟） | ✅ 可信 | 60Hz 的物理步进真实执行 |
| 主循环帧时间（墙钟） | ✅ 可信 | `_process` 之间的真实墙钟差 |
| `PHYSICS_3D_ACTIVE_OBJECTS` / `COLLISION_PAIRS` | ✅ 可信 | 物理服务器真实统计 |
| `OBJECT_COUNT` / `MEMORY_STATIC` | ✅ 可信 | 对象与内存真实分配 |
| `TIME_PHYSICS_PROCESS`（引擎自报） | ⚠️ 只可信"趋势" | 见 1.4，绝对值与墙钟不一致 |
| `RENDER_TOTAL_OBJECTS_IN_FRAME` | ❌ 恒为 0 | dummy 渲染器不产出绘制指令 |
| `RENDER_TOTAL_DRAW_CALLS_IN_FRAME` | ❌ 恒为 0 | 同上 |
| 帧率（FPS） | ❌ | 无头下 `Performance.TIME_FPS` 读到的只是主循环空转速率（实测 ~144），与画面无关 |

**所以本报告只回答"CPU 逻辑与物理要花多久"，不回答"玩家看到多少帧"。**
真实帧率必须在带显示器的环境下测，步骤见第五节。

### 1.2 测的五个场景（主测试共 8 组采样）

| 场景 | 做了什么 |
|------|----------|
| 1. 空场景基线 | 只有玩家 + 地形，**全部敌人 AI 关闭**，无碎片 |
| 2. 碎片满负荷 | 把 `DebrisPool` 抛满 60 个碎片，并**每 20 帧重新抛起**，保证采样期间 60 个刚体持续运动（碎片落地会 sleep，不重新抛的话物理压力会归零） |
| 2b. 碎片静止（对照） | 60 个碎片落地进入 sleep 后不再干预，测"碎片留在场上但不飞"的稳态开销 |
| 3. 完整 Boss 战 | 玩家站到 Boss 身前近战距离，AI 打开，Boss 走完整的选招 / 起手 / 预警圆 / 有效帧 / 收招流程；玩家每 24 帧发一次攻击 |
| 4. 最坏情况 | 60 碎片 + Boss 战 + 额外注入 3 个玩家实体（共 4 人，peer_id 2/3/4），4 个玩家同时出招 |
| 5. 连续破坏 | 用权威入口把 27 块可破坏结构（3 石柱 ×5 + 2 墙 ×6）逐个打碎，每摧毁一个结构采样一次，观察帧时间随碎片数增长 |

每个场景默认采样 **180 个物理帧（3 秒）**，连续破坏的每一步采样 **120 帧**。
采样前有 1~2 秒预热，避免把关卡加载的一次性开销记成每帧成本。
场景之间主动调用 `DebrisPool.clear_all()`，避免上一个场景的碎片在下一个场景采样中途到期消失、污染读数。

### 1.3 两个"帧时间"必须分开看

项目的 `physics/3d/run_on_separate_thread = false`（实测，写在报告开头的说明里），
**物理步进跑在主线程上**。于是 Godot 主循环的每次迭代有两种：

- **含物理步进的迭代**（约每秒 60 次）：这帧顺便推进了一次物理
- **仅脚本的迭代**（其余）：这帧只跑 `_process`

如果混在一起求平均，会得到一个"既不是物理帧也不是脚本帧"的没有意义的中间值。
所以测试把它们分开统计：

- `帧时间-含物理步进` —— **这才是帧时间的大头**，它的倒数是"CPU 侧帧率上限"
- `帧时间-仅脚本` —— 游戏逻辑的下限

### 1.4 一个必须说明的坑：`TIME_PHYSICS_PROCESS` 与墙钟不一致

`TIME_PHYSICS_PROCESS`（引擎自报的物理耗时）与墙钟测出的物理帧间隔
**不一致，且差距随负载放大**：

| 场景 | 物理帧间隔（墙钟） | 引擎自报 `TIME_PHYSICS_PROCESS` |
|------|--------------------|--------------------------------|
| 空场景基线 | 16.66 ms | 0.78 ms（峰值 0.85 ms） |
| 60 碎片飞行 | 16.68 ms | 25.62 ms（峰值 109.22 ms） |
| 上限探针 960 碎片 | 15.46 ms | 135.3 ms |
| 上限探针 3840 碎片 | 82.41 ms | 630.0 ms |

两者同向增长（负载越高读数越大），但**量级差 3~4 倍**，
所以本报告**以墙钟物理帧间隔为主指标**，`TIME_PHYSICS_PROCESS` 只作为
"物理压力随碎片增长而上升"的旁证，不引用其绝对数值下结论。
（这也解释了为什么场景 5 会出现"物理帧间隔 15.8ms、引擎自报却是 128ms"这种表面矛盾。）

### 1.5 测量工具

- 墙钟：`Time.get_ticks_usec()` 在 `_process` / `_physics_process` 里打点，取相邻两次之差
- 是否含物理步进：比较 `Engine.get_physics_frames()` 是否在上一次迭代之后递增
- 统计：平均 / 中位数 / P95 / 最大值 / "超 16.67ms 的帧数" / 三档直方图
- 重要：**只报平均值没有意义**，最大值与 P95 才反映卡顿

### 1.6 关于物理帧间隔的"双峰"

Windows 上 Godot 的物理步进靠内核计时器唤醒，粒度约 15.6ms（不是精确的 16.67ms）。
结果是物理帧间隔普遍呈双峰：大部分帧落在 ~15.6ms，另有一批跳到 ~31ms
（约两个计时器周期，即"这一轮没被准时唤醒"）。**这是计时器量化，不是卡顿。**
所以报告除"超 16.67ms 的帧数"外，还给三档直方图（`<18ms` / `18~28ms` / `≥28ms`），
用来看负载升高时是真变慢还是只是量化抖动。

**从这张表能直接读出的结论：**

1. **在碎片池上限（60）以内，CPU 侧没有崩。** 所有场景的"含物理步进的帧时间"
   平均都在 10.0~11.0ms，帧率上限 ~91~100/s，都还有 60fps 的余量。
2. **碎片数量不是主循环耗时的主导因素。** 空场景基线 10.42ms，碎片满负荷
   10.50ms，最坏情况 10.13ms —— 差异在噪声范围内（同一脚本多次运行，
   基线在 9.8~10.4ms 之间浮动）。
3. **主循环耗时的真正来源是"要不要跑物理步进"本身**，而不是碎片多不多：
   仅脚本迭代只要 4.9~5.8ms，含物理步进就跳到 ~10.3ms。
   这 4~5ms 的差值是**固定成本**（角色、地形、物理服务器步进），
   60 个碎片叠加进去只让帧时间涨了约 0.1~0.7ms。
4. **静态内存对碎片不敏感**：0 碎片 52.9MB → 60 碎片 54.3MB，只涨约 1.4MB
   （池是预分配的，`DebrisPiece` 用 `BoxMesh`，单个碎片开销很小）。
5. **连续破坏到 27 块全碎，帧时间没有随碎片数恶化**（5.1→5.5 在 10.0~11.0ms 之间波动）。
   因为池上限 60 一直没被打满，而且碎片很快 sleep。
6. **负载越高，"含物理步进"与"仅脚本"的差距越明显**：最坏情况（场景 4）
   含物理 10.13ms、仅脚本 5.68ms，差 4.5ms；连续破坏后期（5.4）差 6.0ms。
   这是物理与脚本争夺主线程时间的结果。

### 2.2 最坏情况探针：60 个碎片全程飞行

主测试的场景 2 里，采样窗口内仍有部分碎片落地 sleep。为拿到"限内理论最坏"，
探针让 60 个碎片**每个物理帧都被重新抛起**（活跃刚体恒为 60）：

| 指标 | 数值 | 说明 |
|------|------|------|
| 物理帧间隔 avg / 中位数 / P95 / 最大 | 16.65 / 15.46 / 25.15 / **31.96** ms | 与空场景基线基本一致 |
| 超 20ms 的帧 | 48/239 | 同为计时器量化的尾部 |
| 活跃刚体 | 64 | 恒为 60 碎片 + 玩家/Boss |
| 碰撞对 | 142 | |
| 静态内存 | 55.6 MB | |

**结论：即使 60 个刚体全程飞行，物理帧间隔仍稳定在 16.6ms 附近**，没有越过 60Hz 预算。
（对比空场景基线：物理帧间隔 16.66ms。60 个飞行刚体带来的增量在测量噪声内。）

### 2.3 上限探针：碎片数 → 物理耗时（**这部分数据超出游戏可达范围，仅作参考**）

探针**故意绕过池上限**，直接新建 `DebrisPiece`，找到"物理开始失控"的拐点：

| 碎片数 | 物理帧间隔 avg (ms) | 超 20ms 的帧 | 活跃刚体 | 碰撞对 | 静态内存 |
|--------|---------------------|--------------|---------|-------|---------|
| 0 | 16.66 | 31/119 | 4 | 16 | 52.8 MB |
| 60 | 16.67 | 10/119 | 12 | 94 | 54.5 MB |
| 240 | 16.38 | 10/119 | 194 | 581 | 60.3 MB |
| 960 | 15.46 | 26/119 | 963 | 5043 | 102.0 MB |
| **1920** | **22.82** | **109/119** | 1923 | 12235 | 157.2 MB |
| **3840** | **82.41** | **119/119** | 3843 | 32566 | 347.1 MB |

**拐点大约在 1920 个刚体**：从这一档起物理帧间隔开始稳定超过 20ms；
到 3840 个时平均 82.41ms，意味着物理步进已经无法维持 60Hz。
反过来说，**0→960 个碎片的物理帧间隔几乎没变**，
说明在 1000 个以内物理求解器都还吃得下。

**注意**：`DebrisPool` 的上限是 60，正常游戏**不可能**出现 1920 个碎片。
这个探针的价值是回答"如果哪天把上限调大，多久会出事" —— 答案是**远在 1000 个之前都还安全**，
所以当前 60 的上限非常保守，有充足余量。

**必须打上的诚实标记**：这些高碎片档位的物理耗时膨胀得极快，很大一部分原因是
上千个 `BoxShape3D` 堆叠在同一个平面上互相嵌叠（overlap），
求解器需要反复迭代解算穿透。真实游戏里碎片会散布、会 sleep、会到期回收，
**不会**出现这种持续的"一堆刚体互穿"状态。也就是说 1920/3840 档的数字是
"病态工况的下界"，不能直接外推成"游戏里放 2000 个碎片会掉到 12fps"。

### 2.4 四人联机性能（`bash tests/run_mp_perf_test.sh 4`）

在**同一台机器**上开 4 个 Godot 进程（1 主机 + 3 客户端），4 人进入同一关卡，
每个进程各自抛满 60 碎片，主机发令后各进程同时采样 240 个物理帧。

| 进程 | 本端玩家数 | 碎片 | 物理帧间隔 avg / 中位数 / P95 / 最大 (ms) | 超 16.67ms | 仅脚本迭代 avg / 最大 (ms) | 活跃刚体 | 静态内存 |
|------|-----------|------|------------------------------------------|-----------|---------------------------|---------|---------|
| host (peer 1) | 4 | 60 | 16.60 / 15.59 / 30.51 / **32.91** | 77/239 | 8.43 / **30.66** | 61 | 57.4 MB |
| client A | 4 | 60 | 16.54 / 15.86 / 33.10 / **47.24** | 99/239 | 11.24 / **46.85** | 63 | 54.2 MB |
| client B | 4 | 60 | 16.66 / 15.84 / 38.30 / **48.37** | 102/239 | 11.33 / **46.17** | 60 | 54.1 MB |
| client C | 3 | 60 | 16.67 / 15.84 / 32.64 / **44.87** | 100/239 | 10.76 / **46.34** | 62 | 54.5 MB |

**读法**：

- **主机（跑 Boss AI + 权威结算）的物理帧间隔反而最稳**（P95 30.5ms、最大 32.9ms），
  尾部也最短，因为主机是权威端、位置由自己算，不依赖收包。
- **客户端的尾部明显更长**（P95 32.6~38.3ms、最大 44.9~48.4ms），这是**4 个 Godot
  进程在同一台机器上争抢 CPU + ENet 收包**的结果，不是联机逻辑本身的瓶颈。
- 4 个进程的"仅脚本迭代"要 8.4~11.3ms（单进程时只要 5.3~5.8ms），
  因为要额外处理 3 个远端玩家与网络的同步/插值。
- 物理帧间隔平均仍在 16.5~16.7ms，**没有越过 60Hz 预算**。

**诚实说明**：这是同一台机器上的 4 个进程，**不能**反映跨设备的真实网络延迟、
丢包与不同性能机器之间的时间差。跨设备步骤见 `docs/测试记录.md` 第五节。

## 三、瓶颈分析与优化建议

### 3.1 实测到的瓶颈

**瓶颈 1：物理步进在主线程，是帧时间的固定大头。**

实测：仅脚本迭代 5.4~6.0ms，含物理步进 ~10ms。也就是说**每 6 次迭代里那 1 次
带物理的，多花了 4~5ms**，这几乎占满了 16.67ms 预算的 1/3。
`project.godot` 里 `physics/3d/run_on_separate_thread = false`。
这不是碎片造成的，是"有物理世界"这件事本身的成本。

**瓶颈 2：碎片物理的边际成本很低，但上限一旦放开会失控。**

60 个碎片只让帧时间涨了在噪声范围内的量（不足 0.6ms），可 1920 个就失控（~22.8ms）、
3840 个崩到 ~82ms。
说明成本**不是线性的**，而是随"互穿密度"爆炸。
好消息是当前 60 的上限离失控点还有 30 倍余量。

**瓶颈 3：`GameState.get_alive_players()` 会在玩家被释放后抛异常。**

性能测试场景 4 结束后清理额外玩家时实测触发：

```
SCRIPT ERROR: Trying to assign invalid previously freed instance.
   at: get_alive_players (res://scripts/core/game_state.gd:81)
   [2] _maybe_retarget (res://scripts/enemy/boss_greatsword.gd:460)
   [3] _on_attack_finished_hook (res://scripts/enemy/boss_greatsword.gd:455)
```

`GameState.players` 里残留了被 `queue_free` 但未 `unregister_player` 的引用。
`get_alive_players()` 第 81 行 `var p: Node3D = players[id]` 会把已释放的对象
赋给有类型的变量 —— 这在 GDScript 里是**运行时错误**（不是返回 null）。
Boss 每次攻击结束时都会调 `_maybe_retarget()` → `get_alive_players()`，
所以在"有玩家中途离开/死亡后被回收"的场景下会真的崩。（已记入 K-14。）

### 3.2 优化建议（按性价比排序）

1. **修复 `get_alive_players()` 的无效引用（最高优先，正确性问题）**
   `game_state.gd:81` 改为用带类型擦除的取值再判空，
   例如 `var p: Variant = players[id]` 后 `if not (p is Node3D) or not is_instance_valid(p): continue`。
   同时排查所有 `GameState.unregister_player()` 的调用点，
   确保玩家离场时一定注销。这是 3 分钟就能改完、且能消掉一个真实崩溃的修复。

2. **给碎片物理一个"低速即冻结"的更激进策略（收益明确，风险低）**
   实测数据支撑：碎片全部落地进入 sleep 后，`TIME_PHYSICS_PROCESS` 平均从
   25.6ms 掉到 8.8ms（对照场景 2 与 2b）。
   当前 `DebrisPiece` 已经 `can_sleep = true`，但 `linear_damp=0.42/angular_damp=1.1`
   衰减偏慢，碎片要滚一会儿才停。**把 `linear_damp`/`angular_damp` 调高
   （例如 1.2 / 3.0）能让碎片更快进入 sleep**，把"飞行期"压缩，
   平均物理开销随之下降。这一条不需要改架构，只改两个数。

3. **只在需要时降低碎片上限，而不是无脑调高**
   数据支持：60 → 240 个碎片的物理帧间隔几乎没变（16.53 → 16.50ms），
   但内存从 54.5MB 涨到 60.3MB、碰撞对从 114 涨到 615。
   也就是说**上限的代价主要花在内存与碰撞对管理上，而不是帧时间**。
   如果将来美术上想要更华丽的破坏效果，把 `MAX_DEBRIS_RIGIDBODIES`
   提到 120~150 是安全的（离 1920 的拐点还很远）；超过 240 就没必要了。

4. **不要为解决碎片性能去开 `run_on_separate_thread`（除非先做完整回归）**
   把物理挪到独立线程能把这 4~5ms 从主线程摘出去，但会改变
   `_physics_process` 与 `move_and_slide` 的时序假设，
   项目里联机同步、攻击判定帧都依赖"物理在同一帧内结算"的假设。
   **数据上还没有到需要动这个开关的地步**（限内一切正常），所以不建议现在动。

5. **真实的优化决策要先补上渲染侧的测量**
   本报告完全没有渲染数据。上面所有"还有余量"的结论只对 CPU 成立。
   如果玩家看到的帧率不达标，问题更可能在 GPU（MSAA 2x + 阴影 + 大量
   `MeshInstance3D`），而不是这里的碎片物理。第五节的复现步骤会同时给出渲染侧的观察方法。

## 四、局限（**请务必先读这一节再看数据**）

1. **无头环境没有真实渲染。** dummy 渲染器不产出绘制指令，
   本报告的"帧率上限"是 **CPU 主循环的天花板**，
   **不是玩家实际看到的 FPS**。真实 FPS 一定 ≤ 这个上限（还要扣掉渲染时间）。
2. **`TIME_PHYSICS_PROCESS` 绝对值不可信**（见 1.4），本报告只用它的趋势。
3. **上限探针的第 5、6 档（1920/3840）是人为绕过池上限的病态工况**，
   不代表也不会出现在正常游戏里。
4. **四人联机是"同机 4 进程"**，不是跨设备，不含真实网络延迟与丢包。
5. **未做长时间稳定性测试**：每场景只跑 3 秒，没有跑"连续玩 10 分钟"看内存是否增长。
6. **未测渲染侧的任何指标**（draw call、三角形数、GPU 时间）。
7. 本报告的数据来自**单次机器的一次运行**；物理耗时有 10~20% 的批间波动
   （多次运行观测到基线 9.5~10.4ms 之间浮动），结论（"限内有充足余量"）
   在波动范围内是稳健的，但具体数字不应被当成精确常数引用。

## 五、有显示器的环境下怎么复现（手工步骤）

无头测不出的东西（真实 FPS、渲染耗时、GPU 瓶颈）必须在这里补。

### 5.1 准备

1. 确认 `project.godot` 里 `physics/3d/run_on_separate_thread = false`（当前就是），
   这样下面用 `--print-fps` 测到的帧时间才和本报告可比。
2. 在**有显示器、有 GPU** 的机器上，从项目根目录启动：

   ```bash
   godot --path . --print-fps
   ```

   `--print-fps` 会每秒往控制台打一行 `Project FPS: <n>`。

### 5.2 逐场景对照

按顺序做以下操作，每个场景稳定 10 秒以上再读数，和第 2.1 节的表对照：

| 场景 | 手工操作 | 要记录 |
|------|----------|--------|
| 1. 空场景基线 | 进关卡后**站着不动**，不要靠近 Boss | FPS、物理帧时间 |
| 2. 碎片满负荷 | 按 F3 打开调试面板；走到石柱前连续攻击，把石柱打碎 | 碎片满屏瞬间的 FPS 低点 |
| 3. Boss 战 | 走到 Boss 身前开战，打完一整轮 | 预警圆出现时的 FPS、攻击有效帧时的 FPS |
| 4. 最坏情况 | 4 人联机（见 5.3）+ 同时打碎地形 | 最低 FPS |
| 5. 连续破坏 | 把 3 根石柱 + 2 堵墙**全部**打碎 | 每打碎一根记录一次 FPS |

### 5.3 四人跨设备（同时验证 K-03）

1. 四台机器接同一局域网；主机在主菜单点「创建房间」，记下界面显示的本机 IP。
2. 三台客户端点「加入房间…」，输入主机 IP。
3. 四人全部进入战斗关卡后，主机按 `--print-fps` 观察，
   四台机器同时记录各自 FPS。

### 5.4 用编辑器做更细的观测

在 Godot 编辑器里跑，打开 `调试器 → 监视器`，重点看这几项
（这些在无头下全是 0，必须在有显示器的环境看）：

- `渲染 → 总绘制调用数`（draw call）
- `渲染 → 对象/图元总数`
- `物理 → 3D 活动对象`（对着本报告的"活跃刚体"列比）
- `时间 → 帧 → 帧时间 (ms)`
- `时间 → 物理 → 物理帧时间 (ms)`

### 5.5 判定标准

- **CPU 侧**：物理帧时间稳定 < 16.67ms，且"物理 → 3D 活动对象"数量确实随碎片增长
  （若不增长，说明碎片没在飞，测的不是最坏情况）
- **渲染侧**：draw call 在碎片满屏时不应暴涨（`DebrisPiece` 用的是共享 BoxMesh，
  每个碎片顶多几个 draw call；如果暴涨说明材质没有共享，是个隐藏问题）
- **判定**：如果 CPU 侧（物理帧时间）达标但 FPS 不达标，
  瓶颈在渲染/GPU，应该去优化 MSAA、阴影、材质，**而不是**动碎片上限。

## 六、结论速览

| 问题 | 结论 |
|------|------|
| 碎片满屏（60 个）会掉帧吗？ | **CPU 侧不会。** 60 个刚体飞行时物理帧间隔 16.6ms，含物理的主循环帧时间 10.4ms，离 60Hz 预算还有余量 |
| 四个玩家 + Boss + 碎片呢？ | **CPU 侧仍有余量**，但同机 4 进程时客户端物理帧间隔尾部拉长到最大 45~48ms（进程争抢 CPU，不是逻辑瓶颈） |
| 连续打碎全部 27 块地形？ | 帧时间没有随破坏数量恶化，因为池上限 60 一直没被打满 |
| 那 K-09 到底解决了没？ | **部分解决**：CPU 逻辑与物理侧的瓶颈已经量化并有数据支撑；**渲染侧（真实 FPS）仍必须在有显示器的环境补测** |
| 发现了什么新问题？ | K-12（物理跑在主线程、是帧时间的固定大头）、K-13（碎片边际成本低，但池上限放开后 1000 个以上会失控）、K-14（`GameState.players` 残留无效引用会崩 Boss AI） |
