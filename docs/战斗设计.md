# 战斗设计

本文是战斗系统的设计说明书。所有数值的**来源**与**理由**写在这里；
具体数字存在 `scripts/core/game_config.gd`（全局）与
`resources/weapons/*.tres`（武器）里。

调参前请先读本文倒数第二节"调参速查"。

---

## 一、设计目标（优先级从高到低）

1. **手感**：输入延迟低、动作可预期、状态切换不卡死。
2. **判定可信**：打中了就是打中了，没打中就是没打中，没有模糊地带。
3. **风险回报**：贪刀要付代价，抓住机会有丰厚回报。
4. **可读性**：玩家能用眼睛看出"现在该躲"还是"现在该打"。
5. **视觉表现**：在以上四条成立之后才追求。

**明确不做的事**：不靠堆粒子数量和镜头抖动来伪造打击感。
如果攻击时序、判定精度、动画衔接、敌人反应、操作响应有一项不成立，
再多的特效也救不回来。

## 二、单次攻击的时间结构

本项目的战斗系统建立在一条明确的时间轴上。所有攻击共用这个结构：

```
时刻:  0          windup      windup+active              total
       │             │              │                      │
       ├─────────────┼──────────────┼──────────────────────┤
       │   起手阶段   │   有效判定    │      收招阶段         │
       │  (Windup)   │   (Active)   │    (Recovery)        │
       │             │              │                      │
判定盒: ✗ 关闭        ✓ 开启          ✗ 关闭
玩家可做: 可闪避取消   什么都做不了     可闪避/可连招（过了取消点）
敌人的机会: 读招、走位  必须已经在闪避中  反击窗口 ★
```

三个阶段的**职责**：

| 阶段 | 时长范围 | 作用 | 设计要点 |
|------|----------|------|----------|
| 起手 | 0.20 ~ 1.05 s | 给对手反应时间 | 越长越"重"，越长越容易被躲 |
| 有效 | 0.10 ~ 0.22 s | 唯一能造成伤害的窗口 | 短而明确，不是越长越好 |
| 收招 | 0.34 ~ 1.60 s | **对手的进攻机会** | 这一段比伤害数字更决定战斗是否好玩 |

### 2.1 为什么收招时长最重要

如果所有攻击收招都很短，战斗会变成双方无脑对砍，没有"抓时机"这件事。

本项目的做法是让**收益越高的攻击收招越长**：

| 攻击 | 伤害 | 收招 | 收招/伤害比 |
|------|------|------|-------------|
| 轻击·一之太刀 | 18 | 0.34 s | 0.019 |
| 轻击·三之太刀（终结） | 30 | 0.52 s | 0.017 |
| 重击·蓄力斩 | 45 | 0.60 s | 0.013 |
| 重击·居合斩（蓄力满） | 80 | 0.74 s | **0.009（最划算但最难打出）** |
| 处决·一閃 | 260 | 0.75 s | 0.003（但需要先破防） |

注意居合：伤害最高、单位风险收益最好，但需要 **0.85 秒蓄力**，
期间移动速度受限，而且打空后 0.74 秒无法行动。
这就是"高风险高回报"的具体实现 —— 不是嘴上说说。

### 2.2 判定体积随攻击变化

任务书要求"根据攻击动作变化的判定范围"。实现方式：
每次 `hitbox.activate(attack)` 都按 `AttackData` **重建**
`CollisionShape3D`：

| `shape_type` | 用途 | 例子 | 参数 |
|--------------|------|------|------|
| `Capsule` | 横扫 | 太刀轻击 | `hit_half_length` 0.95~1.35，`hit_radius` 0.50~0.72 |
| `Sphere` | 突刺 / 圆形 AoE | Boss 跳劈 | `hit_radius` 3.2 |
| `Box` | 下劈 / 直线 | 预留 | `hit_half_length` / `hit_half_height` / `hit_radius` |

另外 `hit_offset` → `hit_offset_end` 支持在有效帧内**插值移动**判定盒，
用来表现挥砍轨迹。例如居合斩的判定盒从身前 1.6 m 扫到 2.3 m，
和"冲过去斩一刀"的视觉一致。

判定盒的局部坐标是**相对角色**的，且 `follow_facing = true` 时
随角色朝向实时旋转。这意味着**绕到敌人背后就能躲开横扫** ——
这是"走位有战术意义"的基础。

## 三、玩家操控

### 3.1 移动

| 参数 | 值 | 说明 |
|------|-----|------|
| 普通移速 | 4.6 m/s | 比多数动作游戏略慢，让"走位"有分量 |
| 冲刺 | 7.2 m/s | 按住 Shift。战斗中用不到，赶路用 |
| 加速度 | 42 m/s² | 0.11 秒到满速，起停干脆 |
| 减速度 | 34 m/s² | 松键后 0.14 秒停下，不会"滑冰" |
| 空中操控 | 35% | 跳跃中只有部分控制力 |
| 自由转向 | 720 °/s | 0.5 秒转半圈 |
| 锁定转向 | 540 °/s | 锁定时故意更慢，让"转身"有代价 |

重武器额外降低移速：`weight_class` 为 0.7 的太刀乘 0.958 倍；
若将来做 `weight_class = 2.0` 的巨剑，会乘 0.88 倍。

### 3.2 镜头

结构：`CameraRig`（`top_level = true`）→ `PitchPivot` → `SpringArm3D` → `Camera3D`。

**为什么 `top_level = true`**：角色会旋转（朝向移动方向）。
如果相机支架继承角色旋转，鼠标的水平控制会和角色朝向叠加，
镜头会乱甩。设为 `top_level` 后支架完全由 `CameraRig` 自己控制。

**相机碰撞**：用 `SpringArm3D`，它自动把相机推近以避免穿墙。
`collision_mask` 只含 `world(1)` 和 `destructible(6)` ——
如果含角色层，相机就会被自己顶到脸上。

**两种跟随模式**：

| 模式 | 触发 | 行为 |
|------|------|------|
| 自由 | `GameState.locked_target == null` | 朝向完全由鼠标决定；移动方向相对相机；冲刺时 FOV +最多 6° |
| 锁定 | `locked_target != null` | 自动朝向"玩家与目标之间的构图点"；相机推近到 4.4 m；角色在画面中略偏一侧给 Boss 留观察空间；用鼠标滚轮切换目标 |

**锁定切换为什么用滚轮而不是方向键**：
最初用 A/D（左右移动键）切目标。这是个真实的手感 bug ——
锁定状态下 A/D 正是**横向绕圈走位**最常用的键，
于是每次横移都会跳目标，Boss 和小怪之间疯狂切换、镜头乱甩。
改成鼠标滚轮后不再与任何操作冲突。
切换顺序按"相对当前目标的方位角"排序，是环绕式的，
不会在两个目标之间来回跳。

### 3.3 闪避

| 参数 | 值 |
|------|-----|
| 总时长 | 0.62 s |
| 位移距离 | 4.5 m |
| 无敌窗口 | 0.06 ~ 0.36 s（**净 0.30 秒**） |
| 精力消耗 | 22 |
| 可取消点 | 进度的 72% |

速度曲线用 `2.0 * (1.0 - sqrt(t))`：起步快、收尾急停。
平方根曲线让前 10% 的闪避就走掉约 30% 的距离 ——
这是"闪避要能躲开"的前提，线性曲线会显得粘滞。

**无敌窗口的定位**：0.30 秒既不是"随便滚都能过"（那种会变成
无双游戏的翻滚），也不是"必须帧完美"（那种会劝退休闲玩家）。
配合 Boss 每招 0.62 秒以上的起手，这是一个"看懂了就能躲开"的窗口。

**取消规则**：
- 闪避 **不能** 被攻击打断的有效帧内触发（保证判定可信）。
- 攻击的收招进度超过 `dodge_cancel_progress`（60% ~ 90%，越重的攻击越长）
  之后可以取消成闪避。这让"打完立刻滚开"成为高级技巧而不是默认操作。
- 处决和居合是 100%（不能取消）—— 打空就是真的打空。

### 3.4 锁定

`Q` / 鼠标中键切换锁定。

选目标逻辑（`PlayerController._find_lock_target`）：
1. 只考虑 `lockon_targets` 组、未死亡的目标；
2. 距离 ≤ 24 m；
3. 在镜头前方约 75° 锥内（`dot > 0.25`）；
4. 评分 `distance * (2.0 - dot)` —— 越正对、越近的优先。

锁定时移动基准仍然相对相机，但角色朝向强制对准目标。
**这样"向后撤退"的同时能保持面向 Boss** —— 是类魂战斗的关键操作。

## 四、数值系统

### 4.1 生命值

| 单位 | 上限 | 说明 |
|------|------|------|
| 玩家 | 120 | 能挨 Boss 大约 2~3 下 |
| 训练木桩 | 80 | 用来试伤害，不是来杀人的 |
| Boss | 1400 | 单人需要约 40 秒的持续输出 |

`HIT_INVULN_TIME = 0.25 s`：受击后的无敌时间，防止同一次挥击的
多个判定帧重复扣血。测试 `T5` 专门锁死了这一点（并且刻意把
`invuln_time` 设为 0 来测 `Hitbox` 自己的去重是否也有效）。

### 4.2 精力（Stamina）

类魂战斗紧张感的主要来源。核心不是"消耗"，而是**恢复延迟**。

```
动作消耗精力 → 触发恢复延迟（按消耗量 0.7~2.2 倍缩放）
             → 延迟结束才开始恢复（22/s）
             → 精力降到 0 → 气竭：恢复速度 ×0.55，额外延迟 1.1 s
             → 恢复到 35% 才解除气竭
```

**为什么延迟比消耗量重要**：如果只是消耗快、恢复也快，
玩家可以"打两下等一秒打两下"，节奏是均匀的。
恢复延迟制造了**不均匀**：连续出招会累积延迟，
一旦精力见底就要等很久才能重新行动。

这带来的实际决策是：**"再来一刀，还够不够滚？"**

各动作消耗：

| 动作 | 消耗 | 说明 |
|------|------|------|
| 轻击 1/2/3 | 16 / 17 / 24 | 第三段明显更贵 |
| 重击（含蓄力斩/居合） | 32 | |
| 闪避 | 22 | 与一次轻击同量级，闪避是"有成本"的 |
| 处决 | 0 | 破防的奖励不该再收费 |

满精力 100 大概能做：6 次轻击，或 4 次轻击 + 1 次闪避，或 3 次闪避。
**精力上限不随等级提升**（首版），所以战斗中的资源管理是硬约束。

### 4.3 架势 / 韧性（Poise）

解决的问题：如果敌人每次被轻击都硬直，玩家能无限连死任何敌人；
如果完全不硬直，打击感就变成"打海绵"。

| 单位 | 架势上限 | 恢复速度 | 恢复延迟 | 处决窗口 |
|------|----------|----------|----------|----------|
| 玩家 | 60 | 14 /s | 1.6 s | — |
| 训练木桩 | 40 | 14 /s | 1.6 s | 3.0 s |
| Boss | 160 | 8 /s | 2.2 s | 3.5 s |

**规则**：
- 架势还有余量时，敌人**只播放受击表现**，动作继续（这就是"霸体"）。
- 架势归零 → 进入 `POISE_BREAK` 状态，播放长硬直，**开启处决窗口**。
- 一段时间不被打，架势自动回满。

**破防效率对比（Boss 160 架势）**：

| 手段 | 每下架势伤害 | 需要几下 | 总耗时 |
|------|--------------|----------|--------|
| 轻击一段 | 10 | 16 | ~11.8 s |
| 轻击三段（终结） | 20 | 8 | ~8.6 s |
| 重击 | 34 | 5 | ~6.5 s |
| 居合（蓄力满） | 50 | 4 | ~6.5 s（含蓄力） |

结论：**重击是更高效的破防手段**，但更危险。轻击流也能破防，
但需要更长时间贴身，风险更高。这是一条真实的策略分岔。

Boss 的架势恢复速度只有 8/s（比木桩慢），是刻意设计的：
**鼓励玩家持续进攻而不是打完就跑**。但恢复延迟 2.2 秒意味着
打完一波要停手等待，期间 Boss 会反击。

### 4.4 处决

架势破除后的 3.0~3.5 秒窗口内，玩家可以发动处决攻击
（`katana_execution`，伤害 260）。处决完成后
`PoiseComponent.consume_break()` 结束破防状态。

首版**尚未接线**：`WeaponData.execution_attack` 已配置好，
`BossGreatsword.on_executed()` 也已实现，但还没有
"锁定破防目标时按什么键触发处决"的输入逻辑。
列为阶段 C 待办。

## 五、状态机与打断规则

12 个状态，按**优先级数值**决定谁能打断谁：

| 状态 | 优先级 | 可被谁打断 |
|------|--------|------------|
| 待机 IDLE | 0 | 任何 |
| 冲刺 SPRINT | 0 | 任何 |
| 闪避 DODGE | 40 | 受击(70)、破防(80)、死亡(100) |
| 攻击 ATTACK | 50 | 闪避（仅超出取消点后）、连招、受击(70)、破防(80)、死亡(100) |
| 蓄力 CHARGE | 50 | 同上 |
| 受击硬直 HITSTUN | 70 | 破防(80)、死亡(100) |
| 架势破除 POISE_BREAK | 80 | 被处决(90)、死亡(100) |
| 倒地 DOWNED | 85 | 死亡(100) |
| 被处决 EXECUTED | 90 | 死亡(100) |
| 复活中 RESPAWNING | 95 | — |
| 死亡 DEAD | 100 | 只能被 RESPAWNING 覆盖（复活） |
| 胜利 VICTORY | 100 | 不可打断 |

**规则细节**：
- `request_state()` 检查优先级；同级允许切换（便于攻击接攻击实现连招）。
- `force_state()` 绕过优先级（复活、传送、初始化用）。
- **超时兜底**：每个带时限的状态都有 `_timeout`，
  到点强制回待机。这是防"动作卡死"的最后一道保险。
- `DEAD` 状态不可被除 `RESPAWNING` 外的任何状态覆盖。

### 5.1 攻击的硬性禁止

`AttackController._is_hard_blocked_from_attacking()` 列出了一组
**即使 `force = true` 也不能绕过**的状态：

`HITSTUN` / `POISE_BREAK` / `EXECUTED` / `DEAD` / `DOWNED` / `RESPAWNING`

**为什么需要这一层**：`force = true` 原本是给 Boss 脚本和过场用的，
让它绕过"连招窗口""精力不足"这类*软*检查。但如果它连"正在受击硬直"
都能绕过，就会出现"攻击时序在跑、状态机显示受击硬直"的
**状态不一致** —— 这是动作卡死的主要来源。

软检查（可被 force 绕过）：连招窗口、精力、状态机的 `can_start_attack()`。
硬检查（不可绕过）：上面这组。

## 六、打击感（命中反馈）

任务书 4.4 列出 9 条要求。逐条对应实现：

| # | 要求 | 实现 | 位置 |
|---|------|------|------|
| 1 | 命中时有明确视觉变化 | 目标整体闪白 + 自发光脉冲，重击更强更久 | `HitReactor._start_flash()` |
| 2 | 命中检测可信，不隔空伤害 | 判定盒只在有效帧开启；形状随攻击变化；`follow_facing` 随朝向 | `Hitbox._apply_shape()` |
| 3 | 不同目标有相应音效 | 轻/中/重命中、砍石头、处决各有独立音效键 | `AudioManager.SFX_DEFS` |
| 4 | 命中瞬间的顿帧 | `HitstopManager`，按重量分级 0.045/0.075/0.13 s | 见下方 |
| 5 | 按攻击重量控制镜头反馈 | 轻/中/重抖动 0.055/0.11/0.24；重击有镜头前推 | `CameraRig.add_shake/add_punch` |
| 6 | 敌人受重击有明显反应 | 硬直时长 0.32（轻）/0.72（重）；击退 2.2/6.0 m/s；Boss 霸体但重击仍给 35% 僵直 | `EnemyBase._on_damaged()` |
| 7 | 轻重攻击节奏差异明显 | 起手 0.30/0.55（含蓄力 0.85）；收招 0.34/0.60；顿帧 0.045/0.13 | `katana.tres` |
| 8 | 闪避成功/落空/被打断体验不同 | 闪避有专属音效 + 无敌帧视觉；落空只有挥空音、**无顿帧、无抖动**；被打断会强制结束攻击并进硬直 | `CombatResolver.play_whiff_feedback()` |
| 9 | 声音/特效/动作/伤害一致 | 数值与表现都从同一个 `AttackData` 派生，不存在两处配置 | 架构保证 |

### 6.1 命中停顿（顿帧）的分级

| 等级 | 时长 | 触发 | 时间缩放 |
|------|------|------|----------|
| 无 | 0 | 落空 | — |
| 轻 | 0.045 s | 轻击命中 | 0.04 |
| 中 | 0.075 s | 中击命中（第三段连招） | 0.04 |
| 重 | 0.13 s | 重击/居合命中 | 0.04 |

**关键约束**：绝不用 `Engine.time_scale`。只压攻击者自己的
`AnimationTree.speed_scale`。物理、网络、其他玩家、Boss 的攻击计时
全部照常推进。详见 `技术决策.md` TD-006。

理由不只是"别卡队友" —— 更重要的是**防止玩家用顿帧逃避伤害**：
如果顿帧把 Boss 的起手计时也冻住，玩家的闪避窗口就被动延长了。

### 6.2 三段连招的节奏设计（这是手感的核心）

```
第一段  0.30 起手 ─ 0.10 有效 ─ 0.34 收招    总 0.74 s   18 伤害
        ↑ 可以被"随手按"就出，建立反应速度感

第二段  0.26 起手 ─ 0.10 有效 ─ 0.36 收招    总 0.72 s   21 伤害
        ↑ 略快，让连招有"加速"的感觉

第三段  0.42 起手 ─ 0.14 有效 ─ 0.52 收招    总 1.08 s   30 伤害
        ↑ 明显变慢且收招最长，形成"这一下是终结技"的心理预期
```

如果三段参数一样，连招就只剩下"按键次数"，没有节奏。
第三段的收招 0.52 秒是**故意留的破绽** —— 玩家必须判断
"这一刀打出去，还来得及躲 Boss 的下一招吗"。

### 6.3 命中判定的去重（可信度的基础）

`Hitbox._hit_this_swing` 用 `instance_id` 记录本次挥击已命中的目标。
没有这个，一个跨 6 帧（0.1 s @ 60fps）的有效窗口会把一次攻击
算成 6 次伤害。

测试 `T5` 的做法：把木桩的 `invuln_time` 设为 0（关掉受击无敌），
然后测一次挥击的总扣血是否等于配置伤害。这样 `Hitbox` 自己的
去重逻辑被单独验证，不会因为 `HealthComponent` 的无敌而"假通过"。

## 七、Boss 设计：灰烬巨兵

### 7.1 外形与辨识度

约 3.2 m 高的重甲巨人。轮廓设计：**宽肩、短腿、粗手臂、小头**
（头的尺寸刻意做小，视觉上强调身体庞大）。
面甲上一条横向的橙色暗缝作为"眼睛"，二阶段整体染红。

用基本几何体拼成，成本极低但轮廓一眼可辨。

### 7.2 五种攻击

| 招式 | 判定形状 | 起手 | 收招 | 伤害 | 架势伤害 | 距离 | 设计意图 |
|------|----------|------|------|------|----------|------|----------|
| 巨剑横扫·一段 | 胶囊 | 0.85 | 0.95 | 34 | 22 | ≤5 m 正面扇区 | 基础招式，教玩家"向后或绕背" |
| 巨剑横扫·二段 | 胶囊 | 0.62 | 1.15 | 40 | 26 | ≤5 m 正面扇区 | 更快的变体，惩罚反应慢 |
| 跳劈震荡 | **球** | 1.05 | 1.45 | 52 | 42 | 半径 3.2 m 圆形 | 逼玩家离开近身；地面预警圆最醒目 |
| 冲锋突刺 | 胶囊 | 0.78 | 1.60 | 46 | 34 | 直线长距 | 惩罚只会后退的玩家 |
| **回身斩**（二阶段） | 胶囊 | 0.70 | 1.25 | 44 | 30 | 半径 3.6 m 环形 | 惩罚一直绕背的玩家 |

**每一条都有 0.62 秒以上的起手和 0.95 秒以上的收招。**
这不是保守，是刻意的：类魂战斗的乐趣来自"读懂招式 → 抓住破绽"，
而不是反应速度比拼。

### 7.3 攻击预警（可读性）

两层预警：

1. **动作前摇**：起手期间 Boss 会缓慢转向目标
   （`attack_tracking_speed = 260 °/s`），一旦进入有效帧就锁定方向。
   玩家可以通过"绕得快一点"来躲开 —— 走位有实际意义。

2. **地面预警圆**（仅 AoE 招式）：起手期间在地面显示一个圆，
   颜色随进度从淡变浓，最后 15% 闪烁白光作为最后警告。
   这是"跳劈"这类不能靠走位躲、必须离开范围的招式的唯一提示。

**颜色编码**（`BossGreatsword.TELEGRAPH_COLORS`）：
- 横扫：橙色 —— "来自正面"
- 跳劈：红色 —— "必须离开"
- 冲锋：蓝色 —— "直线，往侧面躲"
- 回身斩：紫色 —— "环形，别站太近"

### 7.4 二阶段

血量降到 60%（840/1400）时：
- 架势强制破除 1.6 秒 + 无敌 1.6 秒（震开周围玩家，给出明确信号）
- 全局攻速 ×0.82（更快）
- 移速 ×1.18
- 横斩伤害 ×1.15
- **解锁「回身斩」**（权重从 0 变为 2.4）
- 整体染红

阶段切换有明确的表现（跪地 → 站起 → 变红），
玩家不会误以为是卡顿。

### 7.5 多人适配（任务书明确要求"不能只靠加血量"）

**Boss 的血量固定为 1400，不随人数变化。** 适配靠行为：

| 人数 | 调整 | 理由 |
|------|------|------|
| 1 | 基准权重 | |
| 2 | 跳劈权重 +1.6，回身斩 +1.28；冷却 ×0.88 | AoE 让围观的人也有风险 |
| ≥3 | 上面继续生效；冷却 ×0.72；冲锋权重 ×0.7 | 进一步压缩站桩输出空间；降低只冲一个人的概率 |

**目标切换**：每次攻击结束后有 55% 概率换目标，
且优先换到**当前离得最远**的玩家（离得远的人往往最安全）——
这是"惩罚躲远处划水"的机制。

**关于"防止 Boss 只攻击一个玩家"**：
权重表让 AoE 招式在高人数下更常出现，这是主要手段。
但必须如实说明：**当前的 AI 仍然是"单体目标 + AoE 混合"，
不是完整的多目标威胁管理**。更完善的做法需要加入
"对每个玩家的威胁值（仇恨）"系统，首版未实现。

## 八、暂不实现的部分（及后续如何扩展）

任务书要求首版不要求复杂防御体系，但**必须说明后续如何扩展**。

### 8.1 格挡 / 招架 / 反击

**预留接口**：
- `DamageInfo.blockable: bool` —— 已存在，当前恒为 `true` 且无人读取。
- `CombatState.State` —— 需新增 `BLOCK`(优先级 45，低于 ATTACK 的 50)
  与 `PARRY`(优先级 55)。
- `CombatResolver.resolve()` —— 在"扣血"之前插入格挡检查：
  ```
  if target 正在格挡 and info.blockable and 攻击来自正面:
      减伤 70%~100%，消耗精力 = 攻击伤害 × 系数
      if 精力不足: 破防 → 进入 POISE_BREAK
      return
  ```
- `HealthComponent` 已有 `is_invulnerable()`，招架可以复用它
  给一段短无敌。

**设计建议**（写给未来的实现者）：
招架窗口必须**远短于**闪避无敌（建议 0.12 s vs 0.30 s），
否则招架会完全取代闪避。招架的回报应该是"大量削架势 + 强制硬直"，
而不是"回血"或"回精力"（那会让战斗变成回合制）。

### 8.2 处决的输入接线

见 4.4 节。需要：
1. 锁定目标时，若目标 `Poise.is_broken`，HUD 显示"可处决"提示；
2. 新增输入动作 `execute`；
3. 玩家在窗口内按该键 → 播放 `execution_attack`
   → 命中后调用 `EnemyBase.on_executed()`。

### 8.3 倒地与救援

`CombatState.State.DOWNED` 已定义（优先级 85）。
需要的是联机流程：
- 玩家血量归零 → 不直接死亡，进入 `DOWNED`，开始倒计时（建议 30 s）；
- 队友靠近按住交互键 N 秒 → 扶起，恢复 30% 血量；
- 倒计时结束 → 真正死亡，回到检查点。

### 8.4 敌人位置同步

见 `架构说明.md` 5.5 的限制 1。需要给 `EnemyBase` 加位置广播。
