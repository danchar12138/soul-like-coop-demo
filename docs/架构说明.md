# 架构说明

本文说明系统的模块划分、接口约定与网络权限。
配合 `AGENTS.md`（开发约束）与 `技术决策.md`（为什么这么做）阅读。

## 一、总体结构

```
                    ┌─────────────────────┐
                    │   Autoload 单例层    │  跨场景常驻
                    │  （见下表）          │
                    └──────────┬──────────┘
                               │ 提供全局服务
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
  ┌───────────┐         ┌───────────┐         ┌───────────┐
  │  关卡层    │         │  角色层    │         │  界面层    │
  │ LevelMgr  │         │ Player /  │         │ MainMenu  │
  │           │         │ Enemy /   │         │ DebugHud  │
  │           │         │ Boss      │         │           │
  └───────────┘         └─────┬─────┘         └───────────┘
                              │ 挂载组件
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
  ┌───────────┐        ┌───────────┐        ┌───────────┐
  │ 战斗组件   │        │ 数值组件   │        │ 表现组件   │
  │ Hitbox    │        │ Health    │        │ HitReactor│
  │ AttackCtrl│        │ Stamina   │        │ Hitstop   │
  │ StateMachi│        │ Poise     │        │ CameraRig │
  └───────────┘        └───────────┘        └───────────┘
```

**分层规则**：上层可以调用下层，下层不能反向依赖上层。
具体说：

- 组件不引用 `LevelManager`、不引用 `MainMenu`。
- 组件之间通过 `EventBus` 信号或明确的 `get_x()` 方法交互。
- 角色脚本只做"输入 → 意图 → 转交子系统"，
  不自己实现攻击时序或伤害计算。

## 二、Autoload 单例

| 名称 | 文件 | 职责 | 不负责 |
|------|------|------|--------|
| `InputSetup` | `core/input_setup.gd` | 运行时注册输入映射 | 读取输入 |
| `EventBus` | `core/event_bus.gd` | 纯信号中转，无状态 | 任何逻辑 |
| `GameConfig` | `core/game_config.gd` | 全局手感参数 | 运行时可变状态 |
| `GameState` | `core/game_state.gd` | 会话状态、玩家注册表、统计 | 权威战斗数据 |
| `AudioManager` | `core/audio_manager.gd` | 音效加载与播放（优先 `assets/audio/*.wav`，缺失时回退到运行时合成） | 音乐、总线效果配置 |
| `DebrisPool` | `terrain/debris_pool.gd` | 碎片对象池与上限控制 | 破坏判定 |
| `TerrainManager` | `terrain/terrain_manager.gd` | 结构注册、破坏结算与同步 | 碎片物理 |
| `NetManager` | `net/net_manager.gd` | 会话建立、权限查询 | 具体状态同步 |
| `DebugHud` | `ui/debug_hud.gd` | 调试面板（F3 开关） | 游戏逻辑 |

**加载顺序很重要**（在 `project.godot` 中按此顺序）：
`InputSetup` → `EventBus` → `GameConfig` → `GameState` →
`AudioManager` → `DebrisPool` → `TerrainManager` → `NetManager` → `DebugHud`。

因为 `_ready()` 里后面的单例会读前面的单例（例如 `StaminaComponent`
读 `GameConfig.STAMINA_MAX`）。Godot 按声明顺序初始化 Autoload。

## 四、核心接口

### 4.1 `EventBus` 信号

**战斗**
| 信号 | 参数 | 触发时机 |
|------|------|----------|
| `attack_started` | `attacker, attack_id` | 攻击起手第一帧 |
| `attack_finished` | `attacker, attack_id, reason` | 攻击结束（含被打断） |
| `attack_landed` | `attacker, target, hit_pos, damage, weight` | 命中角色 |
| `attack_whiffed` | `attacker, attack_id` | 有效帧结束但没打到人 |
| `damage_taken` | `target, amount, remaining, is_heavy` | 扣血完成 |
| `entity_died` | `entity, killer` | 任何单位死亡 |
| `hitstun_started` | `entity, duration, is_heavy` | 进入受击硬直 |
| `poise_broken` | `entity, window_seconds` | 架势破除，开启处决窗口 |

**精力 / 玩家 / 锁定 / 地形 / Boss / 会话** —— 详见
`scripts/core/event_bus.gd` 内的注释，每个信号都写了触发时机。

**约定**：
- `*_requested` 表示意图，可能被否决。
- `*_started` / `*_finished` 表示已确定发生的状态迁移。
- `EventBus` **不用于网络同步**。联机走 RPC。

### 4.2 组件的固定节点名

脚本通过 `get_node_or_null("Health")` 这类固定名字查找组件。
**改名字会静默失效**（找不到就返回 null，不报错），请注意：

| 节点名 | 类 | 必需 | 说明 |
|--------|----|------|------|
| `Health` | `HealthComponent` | 是 | 生命值 |
| `Stamina` | `StaminaComponent` | 玩家/Boss | 精力（敌人可为空） |
| `Poise` | `PoiseComponent` | 是 | 架势 |
| `StateMachine` | `CharacterStateMachine` | 是 | 动作状态 |
| `AttackController` | `AttackController` | 是 | 攻击时序 |
| `Hitbox` | `Hitbox` | 是 | 攻击判定盒 |
| `Hurtbox` | `Damageable` | 是 | 受击盒 |
| `HitReactor` | `HitReactor` | 是 | 受击表现 |
| `Model` | `Node3D` | 是 | 模型根（供染色/倾斜） |
| `HitstopManager` | `HitstopManager` | 自动创建 | 命中停顿 |
| `PlayerSync` | `PlayerSync` | 玩家 | 位置同步 |

### 4.3 攻击管线的单一入口

```
输入 / AI 决策
      │
      ▼
AttackController.request_attack(attack, force)
      │  ① 硬性状态检查（硬直/破防/死亡 → 拒绝，force 也不能绕过）
      │  ② 精力检查（玩家）
      │  ③ 连招窗口检查 → 通过则接续，否则缓冲
      ▼
  _start_attack()  ──► 游戏刻推进 elapsed
      │
      ├─ [0, windup)              起手：判定盒关闭
      ├─ [windup, windup+active)  有效：hitbox.activate()，每帧查重叠
      └─ [windup+active, total)   收招：hitbox.deactivate()，消费缓冲输入
      │
      ▼
Hitbox._check_overlaps()
      ├─ Damageable  ──► DamageInfo ──► CombatResolver.resolve()
      │                                    │
      │                                    ├─ 无敌帧检查
      │                                    ├─ Health.apply_damage()
      │                                    ├─ Poise.apply_poise_damage()
      │                                    └─ 死亡判定 → entity_died
      │
      └─ DestructiblePiece ──► TerrainManager.apply_damage_authoritative()
```

**关键约束**：`CombatResolver.resolve()` 是伤害数值的唯一入口。
任何直接写 `health.health = x` 的代码都是 bug。

## 五、网络架构与权限

### 5.1 拓扑

局域网主机模式（`ENetMultiplayerPeer`）。主机 `peer_id = 1` 即权威端。
最多 4 人（`NetManager.MAX_PLAYERS`）。不做公网匹配、账号、专用服务器。

### 5.2 权限矩阵（重要）

| 数据 | 权威方 | 同步方式 | 频率 |
|------|--------|----------|------|
| 玩家位置 / 朝向 | **该玩家自己的客户端** | RPC 上报主机 → 主机转发 | 20 Hz |
| 玩家动作状态 | 该玩家自己的客户端 | 状态变化时立即上报 + 20 Hz 心跳 | 事件驱动 |
| 玩家生命值 | **主机** | 主机结算后广播 | 事件驱动 |
| 伤害数值 | **主机** | 主机结算后广播 | 事件驱动 |
| 敌人 / Boss 位置与 AI | **主机** | `EnemySync` 主机广播，客户端插值 | 20 Hz |
| Boss 生命值 / 架势 / 阶段 | **主机** | 主机广播 | 事件驱动 |
| 地形耐久与摧毁 | **主机** | 见 TD-007 | 事件驱动 |
| 碎片物理 | **各端本地** | 不同步（纯表现） | — |
| 命中停顿 / 镜头抖动 | **各端本地** | 不同步（纯表现） | — |

**注意两组权威方向是相反的**，这不是笔误：

- **玩家位置**是客户端权威。因为移动手感是第一优先级，让玩家的
  位移等一个 RTT 回包不可接受（TD-008）。
- **敌人位置**是主机权威。因为敌人 AI 需要读所有玩家的状态才能决策，
  而且它的招式选择是加权随机 —— 如果各端各跑一份 AI，
  随机结果会不同，玩家看到的 Boss 出招会和队友看到的不一样，
  也就无法配合闪避。`EnemySync` 顶部的注释详细写了这一点。

**"本地表现"与"权威状态"的分界线**：
碎片、顿帧、抖动、闪避音效、受击闪白 —— 这些**不影响战斗结果**，
各端自己播即可。生命值、伤害、Boss 状态、地形存毁 —— 必须权威。

### 5.3 防重复伤害 / 双重破坏

两个具体机制：

1. **同一次挥击对同一目标只结算一次**：
   `Hitbox._hit_this_swing` 用 `instance_id` 记录已命中目标，
   `activate()` 时清空。没有这个，一个跨 6 帧的判定窗口会把
   一次攻击算成 6 次伤害。（有测试 `T5` 锁死。）

2. **客户端不重算权威结果**：
   客户端命中地形时只发 `_rpc_request_damage` 请求，
   收到 `_rpc_piece_destroyed` 后调用 `force_destroy_from_network()`
   **直接销毁**，不重新扣耐久。这样即使两端延迟不同，
   最终状态也必然一致（因为只有一个地方在做决定）。

### 5.4 玩家生成流程

```
主机启动 → LevelManager._spawn_initial_players()
              │
              for peer_id in NetManager.get_sorted_peer_ids():
                  _spawn_player(peer_id, networked=true)
                      ├─ 加入 Players 容器
                      ├─ set_multiplayer_authority(peer_id)   ← 关键
                      ├─ p.is_local = (peer_id == 本机 peer_id)
                      └─ p.global_position = 出生点[序号]
```

`set_multiplayer_authority(peer_id)` 是所有权分配的核心：
之后该玩家的输入只在他自己的机器上被读取（`PlayerController.is_local`），
位置由他的 `PlayerSync` 上报。

新玩家加入时：主机 `_on_peer_joined` → 延迟 0.4 秒 → `_spawn_player`。
延迟是为了等对方的会话状态就绪。

### 5.5 已知限制（如实记录）

1. **玩家与敌人的位置同步均已实现，并已通过多进程测试**。
   敌人用 `scripts/net/enemy_sync.gd`（**主机权威**，与玩家的
   客户端权威方向相反，原因见该文件顶部的说明）。
   已实测：2 人与 4 人（4 个独立 Godot 进程）。
2. **未在真实跨设备网络上测试**。当前所有联机测试都在同一台机器上
   用多个进程完成，能验证同步逻辑、权限分配与状态一致性，
   但**不能**验证真实网络延迟、丢包、NAT、不同性能机器导致的时间差。
   局域网跨设备测试步骤见 `测试记录.md`。
3. **位置校验是启发式的**，不是完整反作弊（见 TD-008）。
   公网版本必须换成服务端权威位置或加入服务端重放。
4. **倒地救援机制未实现**。当前是死亡 2.2 秒后在检查点自动复活。
   `CombatState.State.DOWNED` 枚举已预留。
5. **未做的联机细节**：
   - 玩家中途断线时没有界面提示（节点会被移除，但玩家看不到原因）
   - 主机迁移：主机退出 = 会话结束，其他玩家无法继续
   - 存档 / 进度同步

## 六、地形破坏的数据结构

任务书要求"地形破坏需要有独立的数据结构，明确记录对象标识、
耐久度、破坏状态和必要的恢复规则"。实现如下：

### 6.1 静态结构（场景中）

```
Terrain/                           （Node3D 容器）
├── PillarEast/                    （StaticBody3D，仅作分组，无碰撞）
│   ├── Piece0  DestructiblePiece  structure_id="pillar_east" piece_index=0
│   ├── Piece1  DestructiblePiece  structure_id="pillar_east" piece_index=1
│   └── ... Piece2/3/4
└── CenterWall/
    └── Piece0..Piece5  DestructiblePiece  structure_id="wall_center"
```

**每个 `DestructiblePiece` 独立持有**：
- `piece_uid`：`"<structure_id>#<piece_index>"`，**全局唯一且各端一致**，
  联机同步靠它定位。
- `max_durability` / `durability`：耐久度。
- `required_weight`：需要的最低攻击重量等级（0 轻 / 1 中 / 2 重）。
  轻击打不动 `required_weight=1` 的石柱下半截 —— 测试 `T10.5` 锁死。
- `is_destroyed`：破坏状态。

### 6.2 运行时聚合（`TerrainManager._structures`）

```gdscript
{
  "pillar_east": {
      pieces:        Array[DestructiblePiece],   # 该结构所有件
      total:         5,                          # 总件数
      remaining:     3,                          # 剩余未摧毁件数（每次变化时重算）
      total_durability: 279.0,
      fully_destroyed: false,
      world_position: Vector3(...),              # 结构中心，用于事件
  },
  ...
}
```

### 6.3 破坏流程与玩法后果

```
攻击命中 Piece
  → Hitbox.destructible_hit 信号
  → AttackController._on_destructible_hit
  → 【权威端】TerrainManager.apply_damage_authoritative()
      → Piece.apply_destruction_damage(amount, weight, impact)
          ├─ weight < required_weight → 只闪一下，不扣耐久
          ├─ durability -= amount
          ├─ _update_damaged_look()   越破越暗越小（逐步损坏）
          └─ durability <= 0 → break_piece()
                ├─ DebrisPool.spawn_from_piece()   生成碎片
                ├─ 碰撞层 6 关闭                    通路立即打开
                └─ queue_free()
      → 【联机】_rpc_piece_destroyed.rpc(uid, impact)
  → TerrainManager._notify_structure_progress()
      └─ remaining == 0 → _complete_structure()
            └─ path_opened.emit(structure_id)
                  └─ LevelManager._on_path_opened()
                        ├─ "pillar_east"  → 关闭 EastFlankBlocker，侧翼路线打开
                        └─ "wall_center"  → 中央通道打开
```

### 6.4 恢复规则

**默认不恢复。** 玩家死亡重生时地形保持已破坏状态。

理由：刚破坏出的通路立刻恢复会让玩家困惑，而且破坏是"有意义的进展"，
不应该因为一次死亡被抹掉。

需要整关重开时调用 `TerrainManager.reset_all()`。

### 6.5 玩法影响（任务书要求"破坏必须改变游戏玩法"）

| 结构 | 摧毁后的影响 |
|------|--------------|
| `pillar_east`（东侧石柱） | 触发 `_open_east_flank()`，关闭 `EastFlankBlocker`，**打开通往 Boss 侧翼的路线** |
| `wall_center`（中央墙体） | 战场中央出现新通道，改变走位与遮挡关系 |
| `pillar_center` / `pillar_west` | 战斗中提供/移除遮挡，影响 Boss 冲锋与横扫的命中 |
| `wall_side` | 同上 |

石柱的**下两截** `required_weight = 1`：轻击打不动，必须用重击或
第三段连招。这制造了一个真实的战术选择 —— 到底是花精力拆柱子
换路线，还是留着柱子当掩体。
